<Section title="Why I built this">

Most of what we send each other online is disposable. Hundreds of messages a day, none of them meaning much. The things that actually matter get buried in the noise.

I wanted to build the opposite. A place where you write one message to one person, share it as a single link, and know it will disappear. The impermanence is the point. It makes both people slow down and pay attention.

Letters started as something much smaller — a personal tool for a personal moment. But I realized early that a tool designed for one person isn't really a tool. It's a gift. And gifts are fragile. If the one person doesn't want it, the whole thing falls apart.

So I rebuilt it for everyone. Same idea, different scope. Anyone can write a letter. Anyone can send one. The design is the same either way: one message, one link, one response, then gone.

Letters has no feed, no likes, no notifications, no tracking, no ads, and no upsells. It exists because I wanted it to exist, and because I think other people might want it too. That's the whole justification.

</Section>

<Section title="What it does">

Letters lets you write one message to one person and share it as a link. The recipient opens it, reads it, and can reply. Then it disappears.

You can customize every part of the letter — the background, the font, the message box, the buttons. Add motion effects: hearts, confetti, snow, fireworks, petals, sparkles. Choose a pattern: Two Choice (Yes/No), One Choice, or Note Only.

Every letter lives on a progressive timer:

- **7 days** from creation
- **3.5 days** after it's been opened
- **1.75 days** after it's been replied to

No feed. No notifications. No likes. No tracking. Just one message, delivered once, then gone.

</Section>

<Section title="The hardest problem: two rendering targets">

Letters has to render identically in two completely different environments:

**1. The live app** — React 19, Motion, Tailwind CSS, TypeScript

**2. The downloaded HTML** — plain HTML, CSS, and vanilla JavaScript

The downloaded HTML cannot run React. It has to be a single file the recipient can save, open offline, and keep. So every visual variant needs a `standalone` version alongside its React component:

```ts
export default {
  id: 'confetti-burst',
  name: 'Confetti Burst',
  component: () => ( /* React component */ ),
  standalone: {
    script: `/* vanilla JS that does the same thing */`,
  },
}
```

Keeping these two renderers in sync was the single biggest engineering problem. A Tailwind class in React has to become a plain CSS rule in standalone. A Motion animation has to become a vanilla `requestAnimationFrame` loop. Every variant, every update, every fix — twice.

The payoff: users can download their letter and it still works in 10 years. No server. No dependency. No company that can shut down.

</Section>

<Section title="Architecture">

The codebase is split into clear layers, with a strict dependency flow:

```text
src/
├── core/          # Shared infrastructure
│   ├── components/   # Reusable UI
│   ├── export/       # HTML + image export
│   ├── lib/          # Utilities
│   ├── seo/          # SEO system
│   └── worker/       # Cloudflare Worker API
├── db/            # Drizzle schema + client
├── letter/        # Letter rendering system
└── pages/         # Route pages
```

**Flow:** `pages → letter → core → db`

Nothing skips layers. Nothing imports upward. Every file has one home, one purpose.

The letter system itself is modular. Each variant — backgrounds, buttons, effects, message boxes, fonts — lives in its own file with its own ID. A Vite plugin auto-discovers them via `import.meta.glob`. Adding a new variant means adding one file. No registration. No config edits.

</Section>

<Section title="Trade-offs I made">

| Decision | Why | Trade-off |
|---|---|---|
| **Cloudflare Workers over Node.js** | Global edge deployment, no servers, no cold starts | Worker runtime limits — no full Node APIs |
| **Drizzle over Prisma** | Smaller bundle, better TypeScript inference, D1-native | Less tooling, fewer tutorials |
| **Better Auth over Clerk/Auth0** | Self-hosted, no vendor lock-in, free | More setup, more code to maintain |
| **Vanilla JS export over iframe** | Truly self-contained download | Two codebases per variant |
| **Progressive expiry over fixed** | Creates urgency, respects attention | More complex state machine |

</Section>

<Section title="What I learned">

Two things.

The first is that reading code is a different skill from writing code. I can read what AI generates now — spot what's wrong, what's missing, what needs to change. That's not the same as being able to write it from scratch. But it's a real skill, and I didn't have it a year ago. It came from reading thousands of lines of code that didn't work, then reading the lines that fixed it.

The second is about shipping. The distance between "it works on my machine" and "it works for the person who needs it" is not the last 5%. It's the whole project. Everything before that is rehearsal. I built the tool. It's done. And I'll be honest: pressing send is harder than building it was. That's a lesson about tools I didn't expect to learn.

</Section>
